# 協調動作の実験(レポート課題)
{: .no_toc }

[準備と動作確認](setup.html) で、ESP32 → Raspberry Pi → ブラウザ、ブラウザ → Raspberry Pi → ESP32 の流れが動きました。
ここからは、AI を使って(または自分で)両方のプログラムを書き換えながら、**通信の仕様を自分で測って**確かめます。
次回からの IoT 設計制作実験では、「何を・どのくらいの頻度で・どのくらいのデータ量で送るか」を自分たちで決めます。その練習です。

## 進め方の基本

- AI は Colab のターミナルで `cd /content/work && agy` として起動します。最初の依頼には「**AGENTS.md を読んでから**」と添えてください。
- ESP32 のプログラムは `/content/work/HttpHaptic/main/main.c`、Raspberry Pi のプログラムは `/content/work/server/app.py` です。
- **Raspberry Pi へのプログラムの送り方**: AI が `app.py` を書き換えたら、ノートブックの「サーバのプログラムを PC にダウンロードする」
  セルでダウンロードし、PC から `scp app.py pi@10.0.1.23:`(IP アドレスは自分の Raspberry Pi の画面に出たもの) で送ります([準備と動作確認](setup.html) の 4. と同じ)。
  Raspberry Pi で `Ctrl+C` してから `python3 app.py` で起動し直すと反映されます。
  小さな変更なら、Raspberry Pi 上で `nano app.py` として直接書き換えてもかまいません。
  `app.py` は Python の標準ライブラリ(`http.server`)だけで書かれています。Raspberry Pi にライブラリを追加しなくて済むよう、
  AI にも標準ライブラリの範囲で書き換えてもらいます(AGENTS.md に書いてあります)。
- **AI は Raspberry Pi と実験室のネットワークに触れません。** サーバの出力やブラウザの表示は、あなたが見て AI に伝えます。
  測るのも人の仕事です。
- 依頼・AI の変更・測った結果は、ノートブックの「AI 利用の記録」の表に書いていきます。
- 実験は当日の後半の約110分で行います。その場でしか確かめられないこと(測る・触る)を優先してください。
  レポートの文章やグラフの清書は、実験のあとでもできます。

## レポート

A4 で 2 ページ程度にまとめ、LMS に個人ごとに提出します。期限は**次週まで**です。
以下の各課題の「**報告すること**」を含めてください。加えて、**AI 利用の要約**(使った AI、主な依頼文 2〜3 個と、
AI の変更が意図と違った点・その原因)を数行で書いてください。ページ数には含めません。

**必須**は課題 1、2-1、3-1(合わせて1時間ほど)です。**選択**の 2-2・3-2 は、必須が終わって時間があれば取り組んでください
(取り組んだ場合はレポートで加点します)。

## 1 時刻も送って、時刻を横軸にグラフを描く

サンプルの ESP32 は `ADC`(A/D 変換値)と `TIME`(ESP32 が起動してからの時刻 [s])を送っていますが、
サーバのグラフは「サーバが受け取った時刻」を横軸にしています。

- サーバのグラフに、**ESP32 の時刻を横軸**にしたものを加えてください(サーバ側の変更)。
- 2つの時刻(ESP32 の時刻とサーバの受信時刻)の差を記録し、その差がどう変わるかを見てください。

**報告すること**: グラフ(力センサを何度か押したところを含む)。2つの時刻の差が何を表しているか、その差が一定でないのはなぜかの考察。

## 2 どこまで速く送れるか、測る(2-2 は選択)

送る間隔は `esp send "interval 200\n"`(ミリ秒)で変えられます。ESP32 の `esp log` には往復時間(`rtt`)が、
ブラウザには毎秒の受信件数が出ます。

1. 間隔を 1000、500、200、100、50、20 ms と短くしていき、それぞれで**毎秒の受信件数**と **rtt** を記録してください。
   設定どおりの件数が届かなくなるのは、どのあたりからですか。
2. **(選択)** 1回のリクエストで1つの値しか送らないのが、速くできない原因の一つです。
   ESP32 が **1 ms ごとに読んだ値を貯めておき、まとめて送る**ように、両方のプログラムを変えてください
   (例: 100 ms ごとに 100 個。送り方(GET のパラメータ、POST、JSON など)は AI と相談して決める)。
   毎秒何個の値をサーバに集められるようになったかを測ってください。

**報告すること**: 1. の表と、限界の原因についての考察。まとめて送ることの利点と欠点(遅れ、データが失われたときの影響など)の考察。
2. に取り組んだ場合は、送り方(1回のリクエストの中身とデータ量)と、測った結果。

{: .tip }
「速く送れるようにして」とだけ頼むと、AI は推測で大きく作り変えます。「何を何個、何 ms ごとに、どの形式で送るか」を
決めてから頼むと、思いどおりになりやすく、レポートの仕様の説明にもそのまま使えます。

## 3 サーバからの指示が届くまでの遅れ(3-2 は選択)

ブラウザで周波数を送ってから、ESP32 の振動が変わるまでには遅れがあります。

1. 送る間隔が 1000 ms と 100 ms のとき、ブラウザで周波数を変えてから `esp log` に `Frequency from server` が出るまでの時間を、
   何回か測ってください(ESP32 の出力の時刻と、サーバの出力の時刻を使うとよい)。
   遅れが送る間隔で決まっている理由を説明し、遅れを小さくする方法を提案してください(間隔を短くする以外の方法も考える)。
2. **(選択)** 提案した方法を一つ選んで実装し、遅れを測ってください。

**報告すること**: 測った遅れ。遅れの原因と、小さくする方法の提案(実装した場合は結果)。

## 発展(余裕があれば)

- **複数台**: 班の ESP32 を 1 台の Raspberry Pi に集め、どの ESP32 からの値かを区別して表示する(何で区別するか)。
- **イベントだけ送る**: 値を一定間隔で送るのではなく、「押された」「離された」ときだけ送る。データ量と遅れはどう変わるか。
- **安全性**: 今のサーバは、同じネットワークにいる誰でも周波数を変えられます。IoT 機器としてどんな問題があり、
  どう防げばよいか(認証、暗号化など)を考える。
- **Colab で解析する**: ブラウザの「記録した値を CSV でダウンロード」で取った `data.csv` を Colab にアップロードし、
  受信間隔のばらつき(ヒストグラム)を AI に描かせる。
